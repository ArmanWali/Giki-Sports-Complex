# Authentication and Session Data Model (Step 6A)

**Document Reference:** `docs/auth-data-model.md`  
**Milestone:** Step 6A (User and Server-Side Session Database Schema)  
**Authoritative Standards:** `requirements-baseline.md` (FR-01, QR-02, QR-13, CR-05)  
**Schema Namespace:** `giki_sports`

---

## 1. Executive Summary & Purpose

Step 6A defines the relational database schema and security invariants for user accounts, role assignments, and server-side sessions in PostgreSQL.

In accordance with project requirements:
- Passwords must be hashed using **salted Argon2id** (QR-13).
- Sessions are **server-side stateful records** expiring after **30 minutes idle or 8 hours absolute age** (QR-13).
- Sessions must support **immediate server-side invalidation upon logout** (QR-13).
- Administrative authority distinguishes between **`sports_director`** and **`super_admin`**; they must not be collapsed into a generic `admin` role.
- **Cashier authority** is treated as a future explicit permission rather than granting financial authority to every staff member.
- Plaintext passwords and raw session bearer tokens must **never** be stored in the database.

> [!NOTE]
> Step 6A establishes the database foundation only. It does **not** implement password hashing algorithms, authentication endpoints (`/api/auth/login`), cookies, middleware, or user registration.

## 2. Core Concepts & Separation of Concerns

To maintain architectural integrity, the data model strictly separates four orthogonal concerns:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        1. Account Identity                             │
│       giki_sports.users: Who the user is (UUID, email, name, status)    │
└───────────────────┬─────────────────────────────────┬──────────────────┘
                    │ 1-to-many                       │ 1-to-many
                    ▼                                 ▼
┌─────────────────────────────────────┐  ┌───────────────────────────────┐
│     2. Role/Authority Assignment    │  │     3. Server-Side Session    │
│  giki_sports.user_roles: What roles │  │ giki_sports.sessions: Active  │
│  the user holds (student, faculty,  │  │ authenticated web/API session │
│  sports_director, super_admin)      │  │ (token_hash, timeouts)        │
└─────────────────────────────────────┘  └───────────────────────────────┘
```

### 2.1 Account Identity (`giki_sports.users`)
- Identifies an individual campus stakeholder.
- Retains canonical identity: primary key `id` (UUID), `email`, `display_name`, account `status` (`active` or `inactive`), and audit timestamps (`created_at`, `updated_at`).
- Does not contain role flags or session states directly on the user row, keeping identity distinct from authorization and active sessions.

### 2.2 Role & Authority Assignments (`giki_sports.user_roles`)
- Authoritative roles:
  - `student`: Standard university student user.
  - `faculty`: University faculty and staff member.
  - `sports_director`: Sports Complex administrator with authority over schedules, closures, announcements, and events.
  - `super_admin`: System administrator with comprehensive administrative and operational authority.
- **Multiple Roles Rationale:** A university stakeholder can hold more than one role (e.g., a faculty member who serves as `sports_director`). Modeling roles in a dedicated join table `user_roles` supports multiple role assignments with relational integrity, without complex array queries or an overly generic permission engine.
- **Cashier Authority:** Cashier financial authority is **not** an all-encompassing staff role. It represents an explicit financial permission that will be modeled in the Digital Wallet & Payments milestone (M5), avoiding granting cash-collection authority to all staff or administrators.
- **Administrative Role Protection:** Administrative roles (`sports_director`, `super_admin`) are assigned internally through authorized workflows; they are never selectable by public users during self-registration.

### 2.3 Password Hash (`password_hash`)
- Stores a salted, formatted Argon2id hash string (e.g. `$argon2id$v=19$m=65536,t=3,p=4$...`).
- Plaintext passwords are never persisted under any circumstances.
- **Important Note:** A `password_hash` column alone does not prove Argon2id is operational; the hashing engine is implemented in Go application code in Step 6B.

### 2.4 Session Token vs. Stored Token Hash (`giki_sports.sessions`)
- **Raw Session Token:** A high-entropy, cryptographically random bearer token generated by the application server (e.g., 32 secure random bytes, hex or base64url encoded). Transmitted to the browser client via an `HttpOnly`, `SameSite=Lax`, `Secure` cookie.
- **Stored Token Hash:** The database stores `token_hash VARCHAR(64) NOT NULL UNIQUE`, which is the SHA-256 hash of the raw token (`SHA-256(raw_token)`).
- **Security Justification:** Token hashing reduces exposure from a read-only database leak: an adversary obtaining database read access cannot directly present stored token hashes as bearer credentials, because SHA-256 is preimage-resistant. However, token hashing does not prevent session hijacking if the raw client-side cookie is intercepted in transit or compromised via XSS.

### 2.5 Dual Expiry Model: Idle Timeout vs. Absolute Lifetime
In accordance with QR-13, a session is considered expired if **either** of two temporal thresholds is reached:
1. **Idle Expiry:** `now >= last_activity_at + 30 minutes`  
   Rejects stale or abandoned sessions when no user requests occur for 30 minutes.
2. **Absolute Expiry:** `now >= absolute_expires_at` (set at session creation: `created_at + 8 hours`)  
   Enforces a strict upper bound of 8 hours, requiring re-authentication regardless of ongoing activity.

#### Concrete Timeline Example

| Wall-Clock Time | User Action / Event | `last_activity_at` | `absolute_expires_at` | Session Status | Rationale |
|---|---|---|---|:---:|---|
| **08:00** | User logs in | `08:00` | `16:00` | **Valid** | Session created with 8h lifetime. |
| **08:20** | User views schedule | `08:20` | `16:00` | **Valid** | Activity updated; idle deadline is now `08:50`. |
| **08:45** | User books slot | `08:45` | `16:00` | **Valid** | Activity updated; idle deadline is now `09:15`. |
| **09:20** | User requests page | `08:45` | `16:00` | **REJECTED** | `now (09:20) >= last_activity (08:45) + 30m`. Idle timeout exceeded. |
| **---** | *(Alternative Scenario: Continuous Activity)* | | | | |
| **15:50** | Active user makes request | `15:50` | `16:00` | **Valid** | Within both idle and absolute limits. |
| **16:05** | Active user makes request | `15:50` | `16:00` | **REJECTED** | `now (16:05) >= absolute_expires_at (16:00)`. Absolute lifetime reached. |

### 2.6 Account Deactivation vs. Session Revocation
- **Account Deactivation (`users.status = 'inactive'`):** Prevents login and instructs application middleware to reject any requests from that account, even if active sessions exist.
- **Session Revocation (`sessions.revoked_at`):** Nullable timestamp. Set to `now()` when a user explicitly logs out or when an administrator revokes a session. Once `revoked_at IS NOT NULL`, the session is immediately dead.

## 3. Relational Schema Specification

### 3.1 Table: `giki_sports.users`

| Column | Type | Nullable | Default | Constraints & Rules |
|---|---|:---:|:---:|---|
| `id` | `UUID` | No | `gen_random_uuid()` | Primary Key. |
| `email` | `VARCHAR(255)` | No | — | Case-insensitive unique; non-empty trimmed string. |
| `display_name` | `VARCHAR(100)` | No | — | User's full name; non-empty trimmed string. |
| `password_hash` | `VARCHAR(255)` | No | — | Encoded Argon2id hash; non-empty string. |
| `status` | `VARCHAR(50)` | No | `'active'` | Allowed values: `'active'`, `'inactive'`. |
| `created_at` | `TIMESTAMPTZ` | No | `now()` | Record creation timestamp. |
| `updated_at` | `TIMESTAMPTZ` | No | `now()` | Record last update timestamp. |

#### Constraints & Indexes
- `uq_users_email_lower`: Unique functional index on `LOWER(TRIM(email))`. Guarantees case-insensitive uniqueness (`user@giki.edu.pk` equals `USER@GIKI.EDU.PK`).
- `chk_users_email_nonempty`: `CHECK (length(trim(email)) > 0)`.
- `chk_users_display_name_nonempty`: `CHECK (length(trim(display_name)) > 0)`.
- `chk_users_password_hash_nonempty`: `CHECK (length(trim(password_hash)) > 0)`.
- `chk_users_status_valid`: `CHECK (status IN ('active', 'inactive'))`.

### 3.2 Table: `giki_sports.user_roles`

| Column | Type | Nullable | Default | Constraints & Rules |
|---|---|:---:|:---:|---|
| `id` | `UUID` | No | `gen_random_uuid()` | Primary Key. |
| `user_id` | `UUID` | No | — | Foreign Key to `giki_sports.users(id)` `ON DELETE RESTRICT`. |
| `role` | `VARCHAR(50)` | No | — | Allowed values: `'student'`, `'faculty'`, `'sports_director'`, `'super_admin'`. |
| `created_at` | `TIMESTAMPTZ` | No | `now()` | Assignment timestamp. |

#### Constraints & Indexes
- `fk_user_roles_user`: `FOREIGN KEY (user_id) REFERENCES giki_sports.users(id) ON DELETE RESTRICT`. Restrictive deletion prevents deleting a user who has active role assignments.
- `uq_user_roles_user_role`: `UNIQUE (user_id, role)`. Prevents duplicate role assignments for the same user while providing an index with `user_id` as the leading column.
- `chk_user_roles_role_valid`: `CHECK (role IN ('student', 'faculty', 'sports_director', 'super_admin'))`.

### 3.3 Table: `giki_sports.sessions`

| Column | Type | Nullable | Default | Constraints & Rules |
|---|---|:---:|:---:|---|
| `id` | `UUID` | No | `gen_random_uuid()` | Primary Key. |
| `user_id` | `UUID` | No | — | Foreign Key to `giki_sports.users(id)` `ON DELETE RESTRICT`. |
| `token_hash` | `VARCHAR(64)` | No | — | Hex-encoded SHA-256 hash of raw session token. Unique. |
| `created_at` | `TIMESTAMPTZ` | No | `now()` | Session creation instant. |
| `last_activity_at` | `TIMESTAMPTZ` | No | `now()` | Instant of most recent authenticated request. |
| `absolute_expires_at`| `TIMESTAMPTZ` | No | — | Absolute ceiling (`created_at + 8 hours`). |
| `revoked_at` | `TIMESTAMPTZ` | Yes | `NULL` | Explicit logout or administrative revocation instant. |

#### Constraints & Indexes
- `fk_sessions_user`: `FOREIGN KEY (user_id) REFERENCES giki_sports.users(id) ON DELETE RESTRICT`. Prevents deleting a user record while session records exist.
- `uq_sessions_token_hash`: `UNIQUE (token_hash)`. Rejects duplicate stored hashes in the database (though it does not mathematically guarantee hash collisions cannot theoretically occur) and generates a B-tree index for fast token validation on every authenticated request.
- `chk_sessions_token_hash_nonempty`: `CHECK (length(trim(token_hash)) > 0)`.
- `chk_sessions_activity_after_created`: `CHECK (last_activity_at >= created_at)`.
- `chk_sessions_expiry_after_created`: `CHECK (absolute_expires_at > created_at)`.
- `chk_sessions_revoked_after_created`: `CHECK (revoked_at IS NULL OR revoked_at >= created_at)`.
- `idx_sessions_user_id`: B-tree index on `user_id`. Optimizes finding or revoking all sessions for a given user (e.g. upon password change or account deactivation).

## 4. SQL Constraints vs. Future Application Logic

| Business / Security Rule | Enforced By PostgreSQL | Enforced by Application Logic | Rationale & Mechanism |
|---|:---:|:---:|---|
| **Case-Insensitive Email Uniqueness** | **Yes** | **Yes** | Postgres index `uq_users_email_lower` guarantees physical database uniqueness; application normalizes input (lowercase, trim) prior to queries. |
| **Non-Blank Mandatory Fields** | **Yes** | **Yes** | SQL `CHECK (length(trim(...)) > 0)` and `NOT NULL` reject empty values; application validates DTOs and returns 400 Bad Request. |
| **Allowed Role / Status Values** | **Yes** | **Yes** | SQL `CHECK IN (...)` prevents invalid string insertion; application enforces typed enums in Go models. |
| **User/Session Referential Integrity** | **Yes** | — | Foreign keys reject orphaned sessions and role assignments. |
| **Restrictive Parent Deletion** | **Yes** | — | `ON DELETE RESTRICT` rejects accidental cascade deletions of user records. |
| **Token Hash Uniqueness** | **Yes** | — | `UNIQUE (token_hash)` rejects duplicate stored hashes in the database. |
| **Logical Timestamp Ordering** | **Yes** | — | SQL checks verify `last_activity >= created`, `expiry > created`, and `revoked >= created`. |
| **30-Minute Idle Timeout** | No | **Yes** | Database stores `last_activity_at`. Application middleware checks `now >= last_activity_at + 30m` and updates `last_activity_at = now()` on valid requests. |
| **8-Hour Absolute Expiry** | No | **Yes** | Database stores `absolute_expires_at`. Application middleware checks `now >= absolute_expires_at` and rejects the request if true. |
| **Immediate Invalidation on Logout** | No | **Yes** | Database stores nullable `revoked_at`. Application logout handler sets `revoked_at = now()`, and middleware rejects any session with `revoked_at IS NOT NULL`. |
| **Argon2id Salted Hashing & Verification** | No | **Yes** | Database stores the formatted hash string. Go `golang.org/x/crypto/argon2` generates salts, computes hashes, and performs constant-time password comparisons. |
| **Secure Token Generation** | No | **Yes** | Go `crypto/rand` generates 32-byte cryptographically secure random bearer tokens; `crypto/sha256` computes the hash before DB storage. |

## 5. Unresolved Decisions & Explicit Exclusions

In accordance with project baseline instructions:
1. **No Assumed University Email Domain Policy:** The schema does not enforce `@giki.edu.pk` or restrict domains via SQL regex. Registration and provisioning policy remains a subsequent stakeholder decision.
2. **No SSO / LDAP Integration Assumed:** The schema is fully self-contained using internal credential hashes and sessions. If external identity provider integration is introduced later, it will link to `giki_sports.users.id`.
3. **No Cashier Module in Migration 3:** Cashier authority is deferred to Module 5 (Digital Wallet & Payments) as an explicit permission.
4. **No Public Administrative Role Assignment:** Self-service registration (when built) will only assign user roles (`student`, `faculty`); administrative roles (`sports_director`, `super_admin`) require internal provisioning.

## 6. GIKI Wallet Codebase Inspection & Adaptation Analysis

Prior to finalizing the Sports authentication schema, the existing authentication subsystem in `giki-wallet/` was inspected:
- Backend authentication module: `giki-wallet/backend/internal/auth/` (`service.go`, `model.go`, `roles.go`, `middleware.go`, `handler.go`, `errors.go`).
- Backend user module: `giki-wallet/backend/internal/user/` (`model.go`, `service.go`, `handler.go`, `user_db`).
- Database schema migrations: `giki-wallet/backend/sql/schema/002_users.sql`, `003_refresh_tokens.sql`.
- Frontend authentication module: `giki-wallet/frontend/src/shared/modules/auth/` (`api.ts`, `validators.ts`, pages, components).

### 6.1 What Wallet Already Provides
1. **Relational User Table (`giki_wallet.users`):** Stores `id` (UUID), `name`, `email` (unique), `phone_number` (unique), `password_hash`, `password_algo`, `is_active`, `is_verified`, `user_type`, and timestamps.
2. **Token Storage Pattern (`giki_wallet.refresh_tokens`, `access_tokens`):** Stores SHA-256 token hashes (`token_hash VARCHAR(64)`) for email verification and password reset rather than raw tokens.
3. **CSPRNG Token Utilities:** Utility in `service.go` (`generateBase64Token`) using `crypto/rand` to generate high-entropy random bytes.
4. **Hash Utilities:** SHA-256 hex encoding (`sha256Hex`) for hashing opaque tokens prior to database storage.
5. **Role-Checking Middleware Pattern:** HTTP middleware in `middleware.go` (`RequireRole(...)`) reading user identity and role from request context.
6. **Structured Domain Error Mappings:** Error declarations (`ErrUserNotFound`, `ErrInvalidCredentials`, `ErrExpiredToken`) mapped to HTTP responses.
7. **Frontend Auth Contract:** API functions (`signIn`, `signUp`, `getMe`, `signOut`, `refreshToken`, `requestPasswordReset`) and Zod validation schemas (`signInSchema`, `signUpSchema`, `resetPasswordSchema`).

### 6.2 What Can Be Reused
In subsequent implementation steps (Step 6B and beyond), the following concepts and utility patterns can be adapted into the Sports codebase without modifying `giki-wallet`:
1. **CSPRNG Opaque Bearer Token Generation:** The `crypto/rand` random byte generator pattern for session tokens.
2. **One-Way Token Hashing:** The `crypto/sha256` hashing pattern before persisting token hashes to PostgreSQL.
3. **Context-Based Middleware Conventions:** The pattern of storing authenticated `userID` and `roles` in Go `context.Context` and checking them via route middleware.
4. **Frontend API DTO Shapes:** Endpoint payload signatures for `/api/auth/login`, `/api/auth/me`, and `/api/auth/logout`.
5. **Client Input Validation Rules:** Email format and non-empty password validation rules in TypeScript.

### 6.3 What Needs Adaptation and Why

| Feature / Area | GIKI Wallet Implementation | GIKI Sports Complex Required Adaptation | Rationale for Adaptation |
|---|---|---|---|
| **Password Hashing Algorithm** | `bcrypt.GenerateFromPassword` (Cost: 10) | **Salted Argon2id** (`golang.org/x/crypto/argon2`) | **QR-13 & CR-05 mandate:** Argon2id provides superior memory-hard resistance against GPU/ASIC offline brute-force cracking. |
| **Session Management Model** | Stateless JWT access tokens + stateful `refresh_tokens` | **Stateful Server-Side Sessions** (`giki_sports.sessions`) | **Requirements & architecture choice:** Server-side sessions were selected as our implementation choice to provide immediate database-driven invalidation upon logout without maintaining separate distributed token revocation lists or bloom filters. |
| **Session Timeout Enforcement** | Fixed JWT expiry (e.g. 15m) + refresh token expiry (e.g. 7d) | **Dual Timeout:** 30-minute idle expiry AND 8-hour absolute ceiling | **QR-13 mandate:** Sessions must reject requests after 30 minutes of inactivity (`now >= last_activity + 30m`) or when reaching 8 hours absolute age (`now >= absolute_expires_at`). |
| **Role Architecture & Authority** | Single `user_type VARCHAR(20)` column (`SUPER_ADMIN`, `TRANSPORT_ADMIN`, `FINANCE_ADMIN`, `STUDENT`, `EMPLOYEE`) | Dedicated join table `giki_sports.user_roles` (`student`, `faculty`, `sports_director`, `super_admin`) | **Requirements mandate:** Separate `sports_director` and `super_admin` without collapsing them into generic `admin`. Dedicated join table permits stakeholders to hold multiple roles (e.g. faculty member who is also sports director). Cashier authority is treated as an explicit future permission under Module 5. |
| **Referential Deletion Semantics** | `ON DELETE CASCADE` on all child tables | `ON DELETE RESTRICT` on `user_roles` and `sessions` | **Audit & Financial Safety:** User accounts linked to audit logs, ledger transactions, or bookings must never be silently cascade-deleted. |
| **Email Normalization & Constraint** | `email VARCHAR(254) NOT NULL UNIQUE` (case-sensitive) | Functional unique index `uq_users_email_lower` on `LOWER(TRIM(email))` + non-empty checks | **Identity Hygiene:** Prevents account duplication via case variations (`user@giki.edu.pk` vs `USER@GIKI.EDU.PK`) or leading/trailing whitespace. |
| **Coupled Subsystems & Dependencies** | Auth service tightly coupled to Redis background jobs (`worker.JobWorker`), transport booking, and external email dispatch | Self-contained authentication without transport, payment, worker, or email dependencies | **Scope Isolation:** Step 6 focuses strictly on core authentication and sessions. Transport, worker, and external mail dependencies are excluded until explicitly required. |
